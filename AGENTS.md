# AGENTS.md

## Назначение репозитория

`gp` — публичное хранилище материалов, подготовленных GPT/Codex для публикации через GitHub Pages.

Основная ветка: `main`.
GitHub Pages публикует содержимое из корня `main`.
Репозиторий является статическим сайтом без обязательного этапа сборки.

## Главное правило размещения

Когда пользователь просит **опубликовать** результат:

1. Если пользователь явно указал подкаталог — использовать его.
2. Если подкаталог не указан — использовать `/s/`.
3. Каждую отдельную публикацию помещать в собственную поддиректорию.
4. Для датированных материалов (с датой в теме или задании) добавлять к имени папки суффикс `-YYYY-MM-DD`; для недатированных материалов дата в slug не обязательна.
5. Имена директорий и файлов по возможности делать ASCII, lowercase, `kebab-case`.

Пример:

```text
gp/
└── ds/
    └── codex-model-report-2026-08-20/
        ├── index.html
        ├── report/
        │   ├── part-01.md
        │   └── ...
        ├── chart.svg
        └── data.csv
```

## Что хранить внутри публикации

Для каждой публикации по возможности сохранять не только конечную страницу, но и исходные материалы:

- `index.html` — единая читаемая веб-версия;
- Markdown-исходники;
- таблицы CSV/JSON, если они были частью расчётов;
- изображения, SVG, диаграммы и другие необходимые ресурсы;
- дополнительные исходные файлы, если без них публикацию трудно воспроизвести или обновить.

Если исходный Markdown очень длинный, разрешено разбивать его на логические части (`part-01.md`, `part-02.md`, ...), а `index.html` собирать их в одну непрерывную страницу.

## Требования к HTML

- Страница должна корректно открываться через GitHub Pages.
- Использовать относительные пути внутри репозитория.
- Не использовать `sandbox:/...`, локальные пути, временные URL или ссылки на файлы из среды ChatGPT/Codex.
- Не использовать `raw.githack`, `rawgit` и аналогичные прокси как основной способ публикации.
- Не привязывать внутренние ресурсы к конкретному commit SHA без необходимости.
- Если HTML загружает Markdown/данные через `fetch`, использовать относительные same-origin URL, например `./report/part-01.md`.
- Страница должна быть адаптивной и нормально читаться на мобильном экране.
- Таблицы должны иметь горизонтальный скролл, если не помещаются по ширине.
- Формулы и Mermaid можно рендерить на клиенте через CDN, если это упрощает статическую публикацию.
- Сохранять UTF-8.

## GitHub Pages

Корень репозитория содержит `.nojekyll`.
Не удалять его без явной причины.

Ожидаемый публичный URL публикации:

```text
https://greenn.github.io/gp/<subdir>/<publication>/
```

Например:

```text
https://greenn.github.io/gp/ds/codex-model-report-2026-08-20/
```

## Корневой индекс

При добавлении новой публикации:

1. Добавить её в корневой `index.html` как отдельную карточку/ссылку.
2. Добавить её в раздел `Публикации` файла `README.md`.
3. Не удалять существующие публикации из индекса без явного указания пользователя.

Корневой `index.html` должен оставаться простым каталогом всех опубликованных материалов.

## Область изменений

При добавлении или обновлении одной публикации:

- в первую очередь менять только её собственную директорию;
- дополнительно менять только корневые `index.html` и `README.md`, если нужно обновить каталог;
- не перерабатывать другие публикации без прямой просьбы пользователя;
- не переименовывать существующие пути без необходимости, потому что они могут быть публично распространены.

## Сохранность опубликованных ссылок

Считать существующие публичные URL стабильными.

Если нужно обновить материал, предпочтительно обновлять файлы **в той же директории**, чтобы ссылка не менялась.
Новый путь создавать только если это новая публикация, новая версия должна существовать отдельно или пользователь просит изменить URL.

## Проверка перед завершением

Перед тем как считать публикацию готовой, проверить:

- есть `index.html` в директории публикации;
- все относительные ссылки ведут на существующие файлы;
- нет `sandbox:` и абсолютных локальных путей;
- нет зависимостей от старого временного репозитория;
- Markdown-части загружаются в правильном порядке;
- изображения/графики отображаются;
- ссылки на CSV и другие загрузки работают;
- корневой индекс содержит ссылку на новую публикацию;
- README содержит актуальную запись;
- существующие публикации не были случайно изменены.

## Git и история

- Не переписывать историю `main` и не делать force-push без прямого указания пользователя.
- Не удалять чужие или старые материалы только потому, что они кажутся неиспользуемыми.
- Не делать массовое форматирование всего репозитория ради локального изменения.
- Коммиты делать небольшими и описательными.

## Приоритет инструкций

Явные инструкции пользователя имеют приоритет над этими правилами.
Если в конкретной поддиректории появится свой `AGENTS.md`, его более специфичные инструкции применяются к этой поддиректории вместе с настоящим файлом.
## Публикации через GP: команда `@gp io`

- Источник команды: приватный ChatGPT-плагин GP (исходники — `greenn/gpp/gp/cur`); **публикации** размещаются в **публичном** `greenn/gp`. Эти репозитории нельзя путать.
- `@gp io` публикует **текущий готовый результат** в `s/<english-kebab-slug>/`. Выбирать короткий, предметный, простой английский slug, например `fractions-practice`; датировку добавлять только к реально датированному материалу.
- `@gp io ds` и `@gp io ds ?url` публикуют подготовленный материал исследования как самостоятельную **интерактивную, адаптивную HTML-страницу** в `ds/<english-kebab-slug>/`. Интерактивность по смыслу: поиск, фильтры/сортировка данных, переходы по оглавлению, переключаемые пояснения; не выдумывать графики и цифры. Сохранять исходный Markdown и доступные проверенные данные, ссылки на источники.
- Аргумент `?url` **необязателен**: URL генерируется и возвращается автоматически после успешного коммита. `?url` не является частью пути, адресом сервера или именем страницы.
- Для любой публикации должны существовать `<category>/<slug>/index.html`, карточка в корневом `index.html` и запись в корневом `README.md`. Все ассеты хранить рядом, только относительные локальные пути, без `sandbox:/` и временных ссылок.
- Перед созданием нового каталога проверить конфликты имён; если путь занят другой публикацией, выбрать другой slug или `-2`, не перезаписывать. При явном обновлении того же материала сохранить прежний URL.
- Страницы публичные: не публиковать секреты, приватные файлы, персональные сведения и неразрешённые защищённые материалы. Не выгружать всю историю чата вместо одного результата.
- Существующий сайт и индексы не удалять; не делать force-push. Обязательны проверка `index.html`, ссылок и итогового коммита. Публичную доступность страницы считать подтверждённой только после HTTP-проверки GitHub Pages; само наличие коммита не доказывает завершение публикации Pages.
- Документация по командам, структуре и проверкам: [`docs/IO.md`](docs/IO.md).
